# 技术架构与统一接口

## 1. 架构目标

技术架构必须保证物理、经济、AI和研发共享一个权威世界，同时允许界面快速预览复杂查询。首发只面向单机：模拟核心与 UI 解耦是为了测试、存档和可维护性，不为未承诺的多人模式预留网络工作。

## 2. 组件边界

### 2.1 Rust 权威模拟核心

建议工作区按领域拆为：

- `sim-time`：TDB 时间、日历显示、事件队列和时间推进。
- `sim-astro`：天体目录、坐标转换、星历与状态查询。
- `sim-trajectory`：Lambert 候选、patched conics、有限推力优化及复核。
- `sim-engineering`：舰船、质量流、功率、热、辐射、寿命与维护。
- `sim-economy`：节点、库存、产消、价格、合同、公司和财务账本。
- `sim-research`：技术图谱、项目、原型、试验、认证和许可。
- `sim-ai`：知识快照、候选计划、评价与命令生成。
- `sim-app`：用例命令、权限校验、事务和对 UI 的查询模型。
- `sim-save`：SQLite 模式、快照、迁移、命令日志和数据包版本。

领域包不得依赖 Tauri、React 或渲染库。所有世界变更必须通过 `sim-app` 命令进入事务。

### 2.2 桌面界面

- TypeScript + React + Vite 负责表格、时间轴、经营面板和交互式地图。
- Tauri 命令是单机进程边界，只传输版本化 DTO，不暴露 Rust 内部对象地址。
- `alpha-v0.1` 使用 Three.js 提供分层浏览、相机缩放和视觉轨道；`alpha-v0.8` 再增加执行级 3D 航迹分析。视觉位置可以连续插值，但不得写回权威状态。
- Web Worker 或 WASM 可运行无副作用的方案预览；最终提交仍由 Rust 核心重新验证。

## 3. 时间、单位与坐标

- 内部基础单位统一为 SI：米、千克、秒、瓦、开尔文；UI 可按上下文显示 AU、km/s、吨和天。
- 游戏绝对时间使用整数微秒表示的 TDB 偏移，并附数据历元；禁止将本地时区作为模拟时间。
- 天体长期星历使用双精度计算；局部积分将位置和时间平移到当前主天体及局部历元，避免大数相减。
- 每个状态矢量必须携带 `frame_id`、`epoch_tdb`、位置和速度，禁止通过字段名暗示坐标系。
- 父子体系采用稳定层级；卫星局部状态可以转换到统一日心惯性参考系。

精度分三级：地图预览、经营规划、执行复核。低精度结果不得直接写入航行事件。

## 4. 核心数据契约

以下字段是逻辑最低集合，实际实现使用带单位的新类型，禁止在领域边界传递无单位裸数。

### 4.1 天体与开发

```text
CelestialBody {
  id, canonical_name, parent_id, body_class,
  mass_kg, mean_radius_m, rotation, ephemeris_source,
  data_quality, discovery_status, development_status
}

BodyState {
  body_id, frame_id, epoch_tdb,
  position_m[3], velocity_mps[3], quality
}
```

`DevelopmentStatus` 只控制任务和经济权限，不控制天体是否进入星历。真实参数、近似参数和虚构参数必须分别标注来源类别。

### 4.2 舰船与航迹

```text
ShipBlueprint {
  id, revision, modules[], dry_mass_kg,
  cargo_capacity, propellant_capacity,
  power_limits, thermal_limits, certification_ids[]
}

VesselState {
  id, owner_id, blueprint_revision, state_vector,
  cargo[], propellant[], condition[], active_plan_id,
  maintenance_due, availability
}

TransferRequest {
  origin, destination, departure_window,
  arrival_window, vessel_id, payload,
  reserve_policy, arrival_condition, allowed_assists[]
}

TransferSolution {
  id, input_hash, solver_version, segments[],
  departure, arrival, propellant_budget,
  power_and_thermal_peaks, lifetime_cost,
  feasibility_margin, validation_level
}
```

只有 `validation_level = Executable` 且输入哈希仍匹配舰船状态的方案可以提交。

### 4.3 经济、研发与 AI

```text
EconomyNode {
  id, location, owner_or_operator, population,
  inventories[], production_lines[], services[], capacities[]
}

Contract {
  id, issuer, cargo_or_service, quantity,
  origin, destination, windows, quality_terms,
  payment_terms, penalty_terms, status
}

ResearchProject {
  id, owner_id, technology_id, stage,
  resource_budget, facility_bookings[], progress,
  risk_state, generated_evidence[], status
}

CompanyKnowledgeView {
  company_id, as_of_time, public_data,
  purchased_intelligence, private_assets,
  forecasts_with_uncertainty
}
```

AI规划器只接收 `CompanyKnowledgeView`，不得持有可访问未来事件或其他公司私有状态的句柄。

### 4.4 世界、事件与账本

```text
ScheduledEvent { id, due_time, priority, kind, payload_version, payload }
GameSnapshot { schema_version, content_version, simulation_time, rng_states, world }
LedgerEntry { id, time, company_id, account, counter_account, amount, cause_id }
InventoryMovement { id, time, node, commodity, quantity, from, to, cause_id }
```

资金和物资变化必须分别形成平衡账本与库存移动记录；事件只引用稳定 ID。

## 5. 应用命令与错误

最小命令集合：

- `QuoteTransfer`、`ValidateTransfer`、`ScheduleVoyage`、`CancelPlan`
- `AcceptContract`、`BidContract`、`LoadCargo`、`BuySupplies`
- `ScheduleMaintenance`、`OrderVessel`、`CommissionFacility`
- `StartResearch`、`BuildPrototype`、`RunTest`、`AcquireLicense`
- `SetTimeRate`、`AdvanceUntil`、`SaveGame`、`LoadGame`

每条变更命令携带 `command_id`、预期世界修订号和操作者公司。失败返回稳定错误代码，例如 `STALE_STATE`、`INSUFFICIENT_FUNDS`、`CAPACITY_UNAVAILABLE`、`SOLUTION_INVALIDATED` 或 `PERMISSION_DENIED`；UI 文案不写入核心。

同一 `command_id` 重试不得重复扣款或创建事件。批量命令要么全成功，要么无副作用失败。

## 6. 星历与航迹计算

1. 天体目录加载并验证父子关系、单位和数据源。
2. 星历服务按时刻请求计算状态并缓存，不逐帧推进全部天体。
3. Lambert 与 patched conics 在出发窗口生成候选。
4. 候选通过有限推力、质量变化、功率和热约束优化。
5. 自适应积分器使用执行级精度复核，产出误差和安全余量。
6. 对时间、工质、载荷、寿命和成本做非支配筛选，形成 Pareto 集。

每种求解器都记录版本、容差、输入哈希和终止原因。无解必须区分物理不可达、约束过严、数值未收敛和搜索预算耗尽。

## 7. 确定性事件推进

- 事件按 `due_time`、`priority`、`id` 排序，同一输入和随机种子得到相同结果。
- 航行按已批准的推力段、滑行段、维护和抵达事件推进；经济按日、人口与宏观产业按月结算。
- `AdvanceUntil` 分段执行所有到期事件，不能越过待玩家处理的阻断事件。
- 时间倍率只控制执行速度，不改变步长、事件排序或随机调用次数。
- 随机源按经济、事故、研发和 AI 公司拆分命名流，避免增加一种事件改变无关结果。

## 8. 存档与内容数据

- SQLite 保存版本化快照、未来事件、账本、命令日志和随机流状态。
- JSON/YAML 数据包保存天体、剧本、货物、部件、技术图谱和 AI 配置；每次存档记录内容版本及校验和。
- 保存采用临时事务与原子替换；异常中断后要么得到旧完整存档，要么得到新完整存档。
- 每次模式变更提供向前迁移和迁移前备份；不支持的数据返回可读错误，不静默丢弃字段。
- 调试导出必须移除本地路径和个人信息，但保留重现所需的世界种子、版本和命令序列。

## 9. 性能与正确性预算

`alpha-v1.0` 基准硬件上的目标：

- 至少 40 个独立天体、30 个经济节点、1,000 艘活动舰船和六家主要 AI 公司。
- 星历单点缓存命中查询小于 5 ms；太阳系地图一帧不得同步触发批量执行级积分。
- 普通两点航迹的首批代表方案目标小于 5 s；完整 Pareto 搜索可后台运行并报告进度、取消和部分结果。
- 日常一天经济结算目标小于 100 ms；一月跳时在无阻断事件时目标小于 2 s。
- 保存与载入标准战役目标分别小于 5 s 和 10 s。

正确性优先于性能。优化前必须保留金标准测试，并对缓存键、并行归并顺序和浮点容差进行显式定义。

## 10. 验证基线

- 单元测试：单位、坐标变换、火箭/功率关系、账本和库存守恒。
- 金标准：公开星历采样、经典两体转移和受控有限推力案例。
- 属性测试：非负质量与库存、合法状态转换、保存载入往返。
- 重放测试：固定种子、相同命令日志在不同时间倍率下产生同一状态哈希。
- 集成测试：航迹询价到抵达结算、研发到认证、AI竞标到交付。
- 性能测试：路线文件定义的规模场景，结果保存为可比较基线。
